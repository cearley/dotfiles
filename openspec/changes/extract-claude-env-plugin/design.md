## Context

This design supersedes an earlier version of this same change that kept several chezmoi-owned partials alive (`claude-env-names`, `claude-env-config`, `claude-environments-bash`) to render machine-specific configuration for the plugin and to preserve bash support. The user redirected: chezmoi's involvement should shrink to a small, fixed set of items — the `.chezmoiexternal.toml.tmpl` entry that pulls the plugin, the `plugins=()` entry that loads it, and the plugin's display-preference settings hosted as literal values in `home/dot_p10k.zsh` (the same way `POWERLEVEL9K_NVM_SHOW_SYSTEM` and every other p10k tuning parameter already work — hand-edited, not chezmoi-templated). Nothing named `claude-env*` should remain in the chezmoi source tree, and the plugin repo location changes to `~/work/zsh-claude-env` (matching the user's existing `~/work` directory, visible in their home directory today).

Mid-design, the user flagged a real gap in that reduction: dropping bash support was described as losing default-`CLAUDE_CONFIG_DIR` propagation to Claude Code's own subagents/Bash-tool invocations. Investigation (Decision 6) showed subagents were never actually at risk — they inherit via OS process environment, not shell config — but surfaced a genuine, narrower gap: no shell got an automatic default outside of the macOS LaunchAgent's GUI-session reach. Decision 7 closes that with one small, explicitly inline (non-partial) addition, bringing chezmoi's footprint to four items instead of three.

This is a substantially bigger architectural change than "extract the code" — it requires the plugin to be self-sufficient without any chezmoi-rendered configuration, which the prior design depended on for the environment-name list, the color map, and the default-environment name.

## Goals / Non-Goals

**Goals:**
- Chezmoi's Claude-environments footprint reduces to a small, fixed set of items: the `.chezmoiexternal.toml.tmpl` plugin source declaration, the `plugins=()` registration, a `dot_p10k.zsh` settings block, and one small inline default-export snippet duplicated in both rc templates (Decision 7).
- The plugin needs zero chezmoi-rendered configuration to discover which environments exist — it must work correctly for a bare `git clone` install with no `config.yaml` anywhere.
- Preserve the `CLAUDE_ENV_SHOW_DEFAULT` toggle from the original request, hosted in `dot_p10k.zsh`.
- The `.chezmoiexternal.toml.tmpl` entry and `plugins=()` registration are specified now, correctly, even though applying them will fail until the plugin repo is actually pushed — sequencing (not scope) handles that.

**Non-Goals:**
- Preserving bash's *interactive* conveniences (wrapper functions, switcher, title hooks, SpecStory wrappers) — explicitly dropped, since oh-my-zsh is zsh-only. (Automatic default-env export is *not* a non-goal — see Decision 7 — it's preserved and extended to bash too.)
- Making the `openspecui` alias part of the plugin — it has no relationship to Claude environments and is relocated to a bare inline alias in the rc templates instead.
- Deciding the fate of `config.yaml`'s now-unused `claude_env_colors` key in this change — flagged, not acted on. (`claude_envs`/`claude_default` remain fully load-bearing for other capabilities — see Decision 8 — and are out of scope entirely, not just deferred.)
- Replacing the validation that `home/.chezmoitemplates/claude-environments` incidentally provided for `claude_envs`/`claude_default` format — accepted as a regression, no replacement built (Decision 8).

## Decisions

**1. Environment discovery via filesystem glob (`$HOME/.claude-*`), not a rendered name list.**
This is the decision that makes "zero chezmoi-rendered configuration" possible. At plugin-load time, the plugin globs `$HOME/.claude-*` directories and generates one `claude-<name>()` wrapper function per match, exactly as the prior design's runtime loop did — except the loop now iterates over glob results instead of a `$CLAUDE_ENV_NAMES` array that chezmoi would otherwise have to render before `plugins=(...)` sources the plugin. The `claude-env` switcher's valid-argument set and the session-index project list (`SESSION_INDEX_PROJECTS`, now also fully plugin-owned) are derived from the same glob.
*Trade-off, scoped correctly after investigation*: in general, a brand-new environment (`~/.claude-neverbefore/` not yet existing on disk) has no wrapper function until the directory exists — bootstrapping it requires one manual `CLAUDE_CONFIG_DIR=$HOME/.claude-neverbefore claude` invocation, after which the next shell session's glob picks it up. This is **not actually a gap in this repo's own usage**: adding a new Claude environment here already means creating a `home/dot_claude-<name>/` chezmoi source directory (containing `modify_settings.json.tmpl`, `symlink_CLAUDE.md.tmpl`, `symlink_skills.tmpl`), and `chezmoi apply` materializes `~/.claude-<name>` as a side effect of managing those files, independent of anything in this change (confirmed for all three of this user's actual environments: `bedrock`, `personal`, `work`). The manual-bootstrap caveat only applies to someone using the *published, standalone* plugin outside this repo's `dot_claude-<name>` convention — documented as a plugin README limitation (task 1.3), not addressed with any chezmoi-side mechanism.
*Alternative considered*: keep an optional `CLAUDE_ENV_NAMES` override variable, merged with glob results, for pre-declaring not-yet-existing environments. Rejected — reopens the "must be set before `plugins=()`" ordering problem this whole redesign exists to eliminate, and the plugin should work identically whether or not chezmoi (or any dotfiles manager) is involved at all.

**2. Display-preference settings (`CLAUDE_ENV_COLORS`, `CLAUDE_ENV_SHOW_DEFAULT`) live in `dot_p10k.zsh`, read only at prompt-render time — never at plugin-load time. No `CLAUDE_ENV_DEFAULT` variable exists.**
This is the key timing insight that makes hosting settings in `dot_p10k.zsh` safe despite it being sourced *after* oh-my-zsh loads the plugin (`plugins=()`/`source "$ZSH"/oh-my-zsh.sh` run early in `dot_zshrc.tmpl`; `[[ ! -f ~/.p10k.zsh ]] || source ~/.p10k.zsh` runs near the end). `prompt_claude_env()` is invoked by p10k on every prompt draw — by the time it first runs, `~/.p10k.zsh` has always already been sourced. So `CLAUDE_ENV_COLORS`/`CLAUDE_ENV_SHOW_DEFAULT` can be declared there with plain `typeset -g`/`typeset -gA` lines and read correctly, with sensible built-in defaults inside the plugin (no color overrides, `SHOW_DEFAULT=true`) for anyone who doesn't set them at all.

There is deliberately no `CLAUDE_ENV_DEFAULT` variable at all (see Decision 7): because the default-export snippet (Decision 7) runs *before* the plugin loads, `CLAUDE_CONFIG_DIR` already holds the correct default value by the time the plugin's `zsh-claude-env.plugin.zsh` first executes. The plugin captures that value once, at its own load time (via the same `_claude_env_name` logic used everywhere else), and uses it internally as the baseline for the show/hide-on-default comparison — no separately-configured "what's the default" variable needed. This is both simpler (one less config variable to document) and more general (works correctly for anyone who starts their shell with *any* `CLAUDE_CONFIG_DIR` already set, dotfiles-managed or not, not just people who've filled in a specific plugin variable).

*Consequence for `CLAUDE_ENV_TITLE_HOOKS`*: this toggle previously needed to be known at hook-*registration* time (inside `plugins=()` load), which would have the same ordering problem if hosted in `dot_p10k.zsh`. Resolved by moving the check from registration-time to invocation-time: the plugin always registers `precmd`/`preexec` hooks, and each hook body checks `$CLAUDE_ENV_TITLE_HOOKS` (and the existing Ghostty-managed check) before doing any work. By the time a hook first *fires* (on the first prompt draw), `dot_p10k.zsh` has already been sourced. Negligible added cost: one cheap comparison per prompt/preexec when hooks are disabled.
*Alternative considered*: keep these as chezmoi-rendered variables (the prior design). Rejected per the user's explicit redirect — they want chezmoi's footprint limited to a small, fixed set of items, none of which is a config-rendering partial.

**3. `.chezmoiexternal.toml.tmpl` entry specified now, using the existing `$zshPlugin` archive pattern; application sequenced after the actual GitHub push.**
Reuses the exact pattern already used for `fast-syntax-highlighting`/`zsh-autosuggestions`/`zsh-defer`/`zsh-autocomplete` (`type = "archive", exact = true, stripComponents = 1`, tarball URL `.../archive/main.tar.gz`), keeping this new entry indistinguishable in style from its siblings. The entry is written into the chezmoi source now (this is a documentation/spec artifact, not yet applied), but a `chezmoi apply` that includes this entry will 404 until `github.com/cearley/zsh-claude-env` exists with content on its default branch. Tasks are sequenced so the GitHub repo is created and pushed *before* the task that runs `chezmoi apply` with this entry live — that push remains an action requiring explicit confirmation when execution actually reaches it, consistent with standing practice for hard-to-reverse, externally-visible actions.
*Not gating the entry on `"ai" .tags`*: the sibling entries in the same `.chezmoiexternal.toml.tmpl` block (inside `{{- if eq .chezmoi.os "darwin" }}`) are not tag-gated — they apply to every darwin machine regardless of tags. Matching that convention, and given the plugin degrades to a complete no-op when no `~/.claude-*` directories exist (no functions defined, no errors), there's no need to additionally gate the `.chezmoiexternal.toml.tmpl` entry or the `plugins=()` line on `"ai" .tags`. This keeps the new entry structurally identical to its siblings rather than introducing a one-off exception.

**4. SpecStory wrappers and the session-index project list move fully into the plugin; the `openspecui` alias does not.**
"Everything self-contained in the plugin" is read literally for logic that's actually about Claude environments (SpecStory's per-env wrapper functions, and `SESSION_INDEX_PROJECTS`, both of which can be derived from the same `$HOME/.claude-*` glob used for wrapper-function generation — no chezmoi involvement needed for either). `openspecui` is different in kind: it's an alias for a completely unrelated tool (OpenSpec UI) that happened to live in the same file for convenience, not because it has anything to do with Claude Code environments. Bundling it into a plugin named `zsh-claude-env` — especially one headed for a public GitHub repo — would be a scope/naming mismatch a future consumer of the plugin would find bizarre. It relocates to a single bare `alias openspecui='npx openspecui@latest'` line directly in `dot_zshrc.tmpl` and `dot_bashrc.tmpl` (gated the same way it always was, `has "ai" .tags`), needing no partial of its own.
*Flagged for reconsideration before publishing*: bundling a specific third-party CLI (`specstory`) into a plugin meant for public consumption is a legitimate but debatable choice; nothing forces it to be removed before publishing, but it's worth a second look at that time, not resolved here.

**5. Bash support is dropped entirely, not migrated.**
No bash-side reimplementation exists anywhere in the new design — chezmoi's reduced footprint has no room for it, and oh-my-zsh (hence the plugin) is zsh-only by construction. This reverses the "preserve bash parity via a small duplicate partial" decision from the prior version of this design. Bash users of this dotfiles repo lose `claude-<name>`, `claude-env`, the terminal-title hooks, `*-spec` wrapper functions, and `SESSION_INDEX_PROJECTS` with no replacement. If bash parity is wanted later, it would need to be a separate, explicitly-scoped change — not attempted here.

**6. Subagents and Bash-tool invocations were never at risk from dropping bash support — verified empirically.**
An earlier draft of this design flagged "bash loses this functionality entirely" as affecting Claude Code's own internally-spawned subagents and Bash-tool commands. That conflated two unrelated things. Verified directly in this session: a Bash-tool shell's process ancestry is `Bash-tool shell → claude (the CLI binary) → the interactive zsh login shell that launched it`, and `CLAUDE_CONFIG_DIR` was present in the Bash-tool shell's environment throughout — inherited via ordinary OS fork/exec environment propagation, with zero dependency on bash's own shell configuration (`.bashrc` isn't even sourced for a non-interactive `bash -c` invocation). Task-tool subagents work the same way, as processes/threads descending from the same `claude` process. Dropping bash's *interactive* wrapper functions/switcher has no effect on this; it only affects a human directly opening a bash login shell and wanting to type `claude-work` themselves.

**7. A small, explicitly non-`claude-env`-named default-export snippet, duplicated inline in both rc templates, restores automatic default-env behavior for every shell.**
Even with subagents cleared (Decision 6), a real gap remained: nothing set a default `CLAUDE_CONFIG_DIR` for shells not covered by the (untouched) macOS LaunchAgent — SSH sessions, and now bash generally too, since it lost its own copy of the old partial's export line. Rather than resurrect a `claude-env`-named partial for this, a ~4-line conditional export is inlined directly into both `home/dot_zshrc.tmpl` (placed before `plugins=(...)`, matching the ordering the plugin needs — see Decision 2) and `home/dot_bashrc.tmpl`, driven by the already-live `claude_default` config.yaml key via `machine-settings` (the same key the LaunchAgent already consumes — this doesn't reintroduce dead configuration, it adds a second small consumer of an existing one). This is treated the same way the `openspecui` alias relocation was handled (Decision 4): small, duplicated, inline, no new partial file — because two near-identical four-line blocks are cheaper than the file-sprawl the user is explicitly trying to eliminate.
*Net effect, a strict improvement over both the immediately-prior draft of this design (which dropped default-export everywhere) and the pre-refactor baseline (which only worked via rc-file export, not LaunchAgent)*: every shell — zsh or bash, local or SSH, GUI-launched or not — now gets the correct default `CLAUDE_CONFIG_DIR` if `claude_default` is configured for the machine.
*Chezmoi's footprint is therefore four items, not three*: the `.chezmoiexternal.toml.tmpl` entry, the `plugins=()` registration, the `dot_p10k.zsh` settings block, and this inline default-export snippet. Flagged explicitly rather than silently expanding scope, since the user's original ask was specifically "three things."

**8. `claude_envs`/`claude_default` format validation is dropped with no replacement; `claude_envs` itself is not dead configuration.**
An earlier draft of this proposal incorrectly claimed `claude_envs` becomes unused chezmoi configuration alongside `claude_env_colors`. It doesn't: `run_onchange_after_darwin-38-install-claude-mcp-servers.sh.tmpl` and `-39-install-claude-plugins.sh.tmpl` both read it via `machine-settings` and loop over every declared environment with `for_each_claude_env` (in `scripts/shared-utils.sh`) to replicate MCP servers/plugins into each `CLAUDE_CONFIG_DIR`; `dot_session-index/config.json.tmpl` reads it directly to build `projects_dirs`. None of these three files are touched by this change and none of them break — but deleting `claude-environments` does remove the *only* validation of `claude_envs`/`claude_default` format anywhere in the repo (the `~/.claude-<name>` shape check and the `claude_default`-must-be-a-member cross-check), which incidentally protected these three consumers too, not just the removed shell feature.

Investigated and rejected two fixes: (a) a new idempotent bootstrap script that both validates and `mkdir -p`s missing environment directories — turned out to be unnecessary, since directory creation is already fully handled by the existing `home/dot_claude-<name>/` source directories (see Decision 1); (b) hardening `for_each_claude_env` with a format-check warning — possible, but explicitly declined.

**Decision: accept the regression, add no replacement.** `for_each_claude_env` already silently skips any declared entry whose directory doesn't exist, which degrades a malformed or undeclared `claude_envs` entry to a quiet no-op identically across every consumer (MCP servers, plugins, session-index, and the shell plugin all skip it the same way) rather than corrupting anything or partially applying. The failure mode — forgetting to create a matching `home/dot_claude-<name>/` source directory when adding a new entry to `claude_envs` — is self-correcting in practice: the environment just doesn't work anywhere, which is an obvious enough signal to notice and fix.

## Risks / Trade-offs

- **[Risk]** A human opening a bash login shell directly loses `claude-<name>`, `claude-env`, title hooks, and SpecStory wrappers, with no chezmoi-side replacement. → **Mitigation**: accepted, explicitly documented (Non-Goals); bash still gets the correct default `CLAUDE_CONFIG_DIR` automatically (Decision 7), so the bare `claude` command still points at the right environment — only the named-environment conveniences are lost.
- **[Risk]** For the *published, standalone* plugin (not this repo's own usage), a brand-new Claude environment has no `claude-<name>()` function until its directory exists and a new shell session re-globs. → **Mitigation**: not a real gap for this repo (Decision 1 — `home/dot_claude-<name>/` already guarantees the directory), but documented as a known plugin limitation in the README for external users (task 1.3).
- **[Risk]** The default-export snippet (Decision 7) duplicates ~4 lines across two rc templates instead of living in one shared partial, reopening a little of the file-count reduction this change is chasing. → **Mitigation**: judged an acceptable, explicit trade-off — matches how `openspecui` was already handled (Decision 4), and two four-line blocks are cheaper to reason about than reintroducing a `claude-env`-adjacent shared partial the user was explicit about eliminating.
- **[Risk]** The `.chezmoiexternal.toml.tmpl` entry, once added, makes `chezmoi apply` fail for every user of this dotfiles repo (i.e., this user, on every machine) until the GitHub repo is actually pushed. → **Mitigation**: strict task sequencing — push the plugin to GitHub *before* the task that adds/applies this entry; do not add the entry to the working tree until immediately before that push is confirmed complete.
- **[Trade-off]** `config.yaml`'s `claude_env_colors` becomes dead configuration (nothing renders it). → **Mitigation**: flagged as a follow-up cleanup, not resolved in this change. (`claude_envs`/`claude_default` are **not** dead — see Decision 8 — this trade-off is narrower than an earlier draft claimed.)
- **[Trade-off]** `claude_envs`/`claude_default` format validation has no replacement after `claude-environments` is deleted (Decision 8), affecting the MCP-servers/plugins/session-index scripts as a side effect, not just the removed shell feature. → **Mitigation**: explicitly accepted — `for_each_claude_env`'s existing silent-skip-on-missing-directory behavior is judged sufficient; the failure mode is self-correcting, not silently corrupting.

## Migration Plan

1. Scaffold `~/work/zsh-claude-env/` (new git repo, uncommitted to any remote) with the self-contained plugin (glob-based discovery, invocation-time toggle checks) plus `README.md`/`LICENSE`.
2. Validate the plugin standalone, then via a temporary symlink under `.oh-my-zsh/custom/plugins/` (same caution as before re: `.oh-my-zsh` being `exact = true` — avoid `chezmoi apply` during that window).
3. Create and push the GitHub repo (explicit confirmation required at execution time).
4. Add the `.chezmoiexternal.toml.tmpl` entry, the `plugins=()` line, and the `dot_p10k.zsh` settings block (`CLAUDE_ENV_COLORS`/`CLAUDE_ENV_SHOW_DEFAULT` only); delete `home/.chezmoitemplates/claude-environments`; remove its `includeTemplate` calls from both rc templates; add the inline default-export snippet and the inline `openspecui` alias to both `dot_zshrc.tmpl` (export placed before `plugins=(...)`) and `dot_bashrc.tmpl`.
5. `chezmoi diff`, then `chezmoi apply`.
6. Full end-to-end re-verification against the real managed files.
7. **Rollback**: `git revert` on the chezmoi commit(s) plus `chezmoi apply` restores the prior (currently-live) `claude-environments` partial behavior; the plugin repo, once pushed, is independent and unaffected by a chezmoi-side revert.
