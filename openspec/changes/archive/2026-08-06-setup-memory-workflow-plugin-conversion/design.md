## Context

See `proposal.md` - Why for motivation. Two facts from that history shape this design directly: (1) the existing `check-drift.sh`/`migrations.sh` check/apply-with-explicit-confirmation discipline has been validated repeatedly and should be preserved wherever this change still needs a check/apply step, rather than reinvented; (2) the `chezmoi-dotfiles`/`chezmoi` basic-memory project rename mixup (2026-07-15) is the concrete precedent behind keeping an override escape hatch for project identity, rather than trusting directory-basename derivation unconditionally.

Plugin mechanics referenced throughout (local marketplace via a plain path, `plugin.json` bundling skills/hooks/MCP, `${CLAUDE_PLUGIN_ROOT}`, per-project `enabledPlugins`, cache at `~/.claude/plugins/cache/`, version resolution order) were confirmed via the `claude-code-guide` agent during brainstorming and are treated here as platform facts, not open questions.

## Goals / Non-Goals

**Goals:**
- Eliminate the class of bug this repo just spent a session fixing: a per-project copy silently drifting from canonical because nothing forced it to update.
- Preserve the parts of today's UX that are working: explicit per-project opt-in, and a check-before-apply/never-silently-overwrite discipline for any remaining local-state mutation.
- Leave `save-session`/`sync-memory` runtime behavior identical from a user's perspective — this is a distribution change, not a feature change.

**Non-Goals:**
- Building general-purpose multi-plugin marketplace tooling. The marketplace scaffold exists to serve exactly one plugin; extending it to host others later is out of scope until there's a second plugin that needs it.
- Solving plugin packaging for other dotfiles-repo tooling in general.
- Any change to how basic-memory itself is installed or how its MCP server is registered globally.

## Decisions

**Single monolithic plugin, not split by concern.** `save-session`, `sync-memory`, and the hook ship as one plugin (`basic-memory-workflow`). Considered splitting `sync-memory` into its own plugin for finer-grained opt-in, but `sync-memory` is already `disable-model-invocation: true` — inert until explicitly run — so a separate enablement toggle wouldn't gate any behavior a project doesn't already implicitly consent to just by having the plugin present. Two manifests for zero behavioral difference isn't worth the bookkeeping.

**Plugin content lives outside `home/`, entirely untemplated.** `.claude-plugin/marketplace.json` and `plugins/basic-memory-workflow/` sit at the chezmoi source root as plain files. Claude Code's own plugin cache (`~/.claude/plugins/cache/...`) is what actually distributes this content to consuming projects — chezmoi's job shrinks to one thing: getting the marketplace *registered* on a new machine. Templating plugin content through `home/` was considered and rejected as pure redundancy: it would reintroduce a chezmoi-apply step doing exactly what the plugin cache mechanism already does natively.

**Local marketplace inside this repo, not a standalone published repo.** Unlike `zsh-claude-env` (generically useful outside this dotfiles setup, hence its own public repo), this plugin is tightly coupled to this user's specific basic-memory/SpecStory conventions. A standalone repo would add publishing overhead with no reuse benefit.

**Marketplace registration via a dedicated `run_onchange_` chezmoi script calling the real `claude plugins marketplace add` CLI, not hand-edited `known_marketplaces.json`.** This repo already has a working, data-driven mechanism for remote marketplaces/plugins: `home/.chezmoidata/packages.yaml`'s `ai.agents.claude_code.plugin_marketplaces`/`.plugins` lists, consumed by the existing `run_onchange_after_darwin-39-install-claude-plugins.sh.tmpl` via `claude plugins marketplace add <source> --scope user` / `claude plugins install <plugin> --scope user`, looped over every `claude_env` via `for_each_claude_env`. Two things rule out reusing that script directly: (1) `.chezmoidata/` files are static — our marketplace source is the self-referential `{{ .chezmoi.sourceDir }}`, which cannot appear in a non-templated YAML file; (2) that script's `plugins:` list installs at `--scope user`, meaning *every* project in that environment gets the plugin — the opposite of the per-project opt-in this design requires (confirmed by the file's own `# Project/local-only plugin` comments marking entries deliberately excluded from that list for the same reason). So: a small new script registers *only* the marketplace (never installs/enables the plugin itself), reusing this repo's `for_each_claude_env` + `CLAUDE_CONFIG_DIR` + warning-on-failure pattern from script-39, calling `claude plugins marketplace add "{{ .chezmoi.sourceDir }}" --scope user` directly rather than reimplementing idempotency by hand-parsing `known_marketplaces.json` — the CLI itself is trusted to handle re-adding the same source safely, the same trust this repo's own script-39 already places in it.

**basic-memory's global MCP registration mechanism, corrected.** proposal.md originally attributed this to the `claude-extend` tools.json mechanism referenced in this repo's root `CLAUDE.md`. It is actually the same `packages.yaml`/script-38 mechanism described above (`mcp_servers:` list, `run_onchange_after_darwin-38-install-claude-mcp-servers.sh.tmpl`) — `basic-memory` is already a `mcp_servers` entry there. The conclusion is unchanged (already handled globally, out of scope for this change), only the mechanism name was wrong.

**Project identity: shared runtime-resolution script with a file-based override, not pure git-derivation.** Pure `git rev-parse` + `basename` was the simpler option and was seriously considered, but it silently reintroduces the exact failure mode from the 2026-07-15 mixup if a project's basic-memory identity ever needs to diverge from its directory name again. The override file (`<project-root>/.claude/basic-memory-project.txt`) is a deliberately narrow escape hatch — checked first, used only if non-blank, otherwise falls through to the same derivation pure git-derivation would have used.

**Migration as a bundled idempotent script, not a one-off manual cleanup.** `migrate-to-plugin.sh` reuses `check-drift.sh`'s check/apply shape rather than being a throwaway script run twice by hand for the two currently-known targets. This costs little extra and means any future project that still has old-style artifacts gets the same safe, reviewable cleanup path without needing bespoke steps re-derived from memory.

**Plugin enablement goes through `claude plugin install <plugin>@<marketplace> --scope local`, not a raw `jq` write to `enabledPlugins`.** Verified empirically during implementation: that CLI command writes the same `enabledPlugins` key in `.claude/settings.local.json` a hand-rolled `jq` edit would — but it *also* materializes the plugin into this machine's cache (`~/.claude*/plugins/cache/...`) and records it in `installed_plugins.json`. A hand-written `enabledPlugins` entry alone would leave nothing for Claude Code to actually load. `--scope local` lands in `.claude/settings.local.json` specifically (not `.claude/settings.json`), matching where the old per-project hook config lived — personal-machine scope, typically gitignored. A project team that wants the plugin enabled for everyone can still choose `--scope project` instead (writes `.claude/settings.json`); `migrate-to-plugin.sh` defaults to `local` but doesn't prevent a manual switch, the same way the old system left `.mcp.json`'s gitignore status to the user.

**Project registration and the basic-memory-installed check move from one-time install to idempotent per-invocation checks inside `save-session`.** Removing the installer skill removes the one place these checks used to run. Since `basic-memory project add` is already idempotent (exits 0 with a notice if already registered) and a `which basic-memory` check is cheap, running both at the start of every `save-session` invocation is simpler than inventing a separate "first run in this project" concept — which would just reintroduce an install step under a different name.

**Omit `version` from `plugin.json`.** Per the confirmed plugin versioning behavior: omitting `version` means every commit is a new version and consumers auto-update; setting it pins consumers until the string is manually bumped. Pinning would recreate the exact "someone has to remember to bump a marker" pattern this whole change exists to eliminate — so `version` stays unset, deliberately.

## Operational note: refreshing a local-directory plugin's cache

Discovered during implementation: `claude plugin update <plugin> --scope <scope>` compares against a cached *version identifier* (for a local git-repo-backed marketplace source, this appears to be the repo's `HEAD` commit SHA, not a live content hash) — it does **not** detect edits to the plugin's files while the source repo's working tree is dirty. `update` reported "already at the latest version" even after `hooks/hooks.json` was fixed. The reliable way to force Claude Code to re-copy current on-disk plugin content into its cache is `claude plugin uninstall <plugin>@<marketplace> --scope <scope> -y` followed by `claude plugin install <plugin>@<marketplace> --scope <scope>` again. Also note both `update` and any cache change require restarting the Claude Code session that should pick it up — plugins load at session start, not live.

## Risks / Trade-offs

- **[Risk]** The plugin system is newer and less battle-tested in this repo than `check-drift.sh`, which has been iterated on and fixed repeatedly. → **Mitigation**: `migrate-to-plugin.sh` keeps the identical check/apply, confirm-before-overwrite discipline. Task list includes an explicit smoke test (register marketplace, enable plugin, verify hook fires, verify skills load) against this chezmoi repo before deleting anything.
- **[Risk]** `resolve-project-name.sh` runs as a subprocess on every `save-session`/`sync-memory` invocation and every `SessionStart`, instead of reading a pre-baked string. → **Mitigation**: cost is one `git rev-parse` and one file-existence check — negligible, and `sync-memory.py` already does a runtime `git rev-parse` for its filesystem root today.
- **[Risk]** The override file itself could go stale (e.g. an intentional rename happens and nobody updates it) with no automatic staleness detection, mirroring the class of bug the old `NAME-MISMATCH` check used to catch. → **Mitigation**: explicitly out of scope — this is a rare, manually-maintained escape hatch, not the default path; automatic staleness detection can be added later if it actually bites.
- **[Risk]** `migrate-to-plugin.sh apply` deletes directories and edits settings/exclude files in this repo's own live `.claude/` state and in other real projects. → **Mitigation**: check-then-apply-only-on-confirmation, plus reviewing `git status` of affected paths before deletion, consistent with this session's standing safety practice for destructive-ish operations.
- **[Risk, materialized]** Not every real project is on the same prior `setup-memory-workflow` vintage. `migrate-to-plugin.sh` initially only checked the v8+ `SessionStart` hook shape; a real external project (`viewpoint-report-automation`, `setup-memory-workflow-version:2`) was still on the *pre-v8* `UserPromptSubmit` shape (the one this repo's own `check-drift.sh` `migrate_hook_config()` already knew to clean up) and was silently left behind by the first `apply` run against it. → **Fix applied**: `migrate-to-plugin.sh` now independently detects and removes both hook shapes, guarded separately so mutating one never assumes the other's key exists. Verified against a fixture reproducing the exact shape. **Follow-up required**: any project already `apply`'d before this fix (confirmed: `viewpoint-report-automation`) needs `apply` re-run to pick up the `UserPromptSubmit` cleanup — safe to re-run, everything else is already a no-op there.

## Migration Plan

1. Build the plugin package and marketplace scaffold in this repo. Leave `home/dot_claude/skills/setup-memory-workflow/` in place, untouched — old and new systems coexist during rollout.
2. Add and apply the `run_onchange_` marketplace-registration script on this machine; verify registration is idempotent (re-run `chezmoi apply`, confirm no duplicate entry).
3. Enable `basic-memory-workflow` for this chezmoi repo as the first real target; verify `save-session`, `sync-memory`, and the `SessionStart` hook all behave identically to today's copy-based install.
4. Run `migrate-to-plugin.sh check` then `apply` against this repo; verify old artifacts are gone and `enabledPlugins` is set correctly.
5. Run the same `check`/`apply` against `~/work/WES.ViewPoint.ExternalIntegration.FulcrumAppAPI`.
6. Only once both known targets are confirmed working: delete `home/dot_claude/skills/setup-memory-workflow/` in full.

**Rollback**: until step 6, the old skill is untouched and fully functional — any problem found in steps 2-5 is resolved by simply not enabling the plugin or not running `apply` yet. After step 6, rollback would mean restoring the deleted directory from git history, which is why deletion is deliberately the last step, gated on both targets working.
