# Design

## Context

See `proposal.md` — Why, for motivation. Relevant current-state facts this design depends on, confirmed by reading `home/dot_claude/skills/setup-memory-workflow/scripts/executable_check-drift.sh` directly at its current state (post-`memory-workflow-sessionstart-improvements`, `SMW_VERSION=17`):

- `extract_open_excerpt()` reads the current-status note via `resolve_status_note_path()` (a glob against `$HOME/.local/share/basic-memory/$PROJECT/status/`, case-insensitive, excluding `*archive*` siblings), extracts the `## Open` section, and caps it at 15 bullet-boundary-aware lines.
- `render()` substitutes `__OPEN_EXCERPT__` into `hook-message.txt.template` via bash-native `${content//pattern/replacement}`, computed at `check`/`update`/`apply hook-config` time, not at hook runtime.
- `cmd_drift_warn()` already has one note-bloat check (current-status note only) using `save-session-maintenance`'s thresholds (≥8,000 chars, ≥200 lines, or any single line ≥800 chars), plus the pre-existing save-session-skill version-drift line. Both are independent, additive signals in the same function, each guarded to degrade silently (no error, exit 0) on a missing file.
- `cmd_check()`'s `== SessionStart hook ==` block does a single `[ "$existing_cmd" = "$canonical_cmd" ]` string comparison; anything that differs (and whose embedded project name still matches) is reported as generic `DRIFT`, with no finer-grained distinction.
- `save-session-maintenance-skill.md.template` independently defines a **second** threshold this skill's drift-warn has never surfaced: the active session-log note gets rolled over once it reaches 300 lines (Step 1 of that skill). Confirmed via `grep` against the live template (`home/dot_claude/skills/setup-memory-workflow/assets/save-session-maintenance-skill.md.template:47-64`).
- The main spec's existing "Active session-log note is resolved deterministically, not by search" requirement describes how `save-session`'s own Step 1 finds the *active* session-log note: the most recent wikilink in the current-status note's Status Summary section. That resolution logic lives in `save-session`'s prose instructions (interpreted by the model via MCP reads), not in `check-drift.sh` — there is no existing bash reimplementation of it, and `check-drift.sh` has no MCP access to verify one if it had.
- A live hcom comparison (2026-11-07, `kali` for oh-my-claudecode, `muse` for oh-my-pi's own agent-memory backend, `raza` for Claude Code's own session mechanics while working in the oh-my-pi repo — which turned out to be this same skill, confirming a real, unforced instance of version drift on another machine) is the direct source of the four functional changes below. No new exploration was needed beyond re-reading the current script and template, since the gaps are all narrow extensions of mechanisms that already exist.
- A follow-on review of this design (same day) surfaced a separate, conceptual issue, not from the comparison: `extract_open_excerpt()`, `resolve_status_note_path()`, and the note-bloat portion of `cmd_drift_warn()` — all added by the prior change — read live, user-generated basic-memory note content. That's a different concern from `check-drift.sh`'s own stated job (its header comment: "mechanical checks and safe/idempotent actions for the setup-memory-workflow skill," i.e. comparing installed pieces against canonical templates, driven only by `$PROJECT`/`$SMW_VERSION`/the skill's own asset files). Nothing about reading a user's evolving note content fits that shape, and this change's own session-log-bloat addition (Decision 2 below) would otherwise double down on the same conflation rather than correcting it.
- `scripts/migrations.sh` is the existing precedent for factoring a distinct concern out of `check-drift.sh` into its own sourced file while keeping a single invocation point: no shebang, not executable, sourced only (`source "$SKILL_DIR/scripts/migrations.sh"`), its functions take no arguments and rely on globals (`$PROJECT_ROOT`) already set by the sourcing script, and its own header states a narrow contract ("Operates on the relevant file under `$PROJECT_ROOT`... MUST be idempotent... Called unconditionally, once, near the top of check-drift.sh").
- A separate, user-raised issue (same day, unrelated to the comparison): `executable_crash-recovery-hook.sh` (confirmed by reading it directly) compares only session-ID *identity* — the most recently modified prior transcript's session ID against the bare session ID recorded in `.claude/.last-saved-session` by `save-session`'s three marker-writing spots (`assets/save-session-skill.md.template:47,59,128`). This has two real failure modes: (a) a false positive whenever `/clear` starts a new session that ends without saving, however small, since its session ID will never match the marker; (b) a false negative whenever a session saves early then keeps going — the marker still matches that session's ID no matter how much unsaved work piles up afterward, so nothing fires even for a genuine crash losing dozens of turns.
- Verified empirically against this project's own real transcripts (`~/.claude/projects/-Users-craig--local-share-chezmoi/*.jsonl`): `type=="user"` entries include both genuine human-typed turns (`message.content` as a plain string, or `isMeta:false`) and synthetic entries that are not real turns — tool-result echoes (`toolUseResult != null`) and skill/local-command-injected content (`isMeta:true`, confirmed by inspecting actual content: skill bodies, `<local-command-caveat>` blocks). The correct turn-counting filter is `select(.type=="user" and (.toolUseResult // null)==null and (.isMeta // false)==false)`.
- Verified via `claude-code-guide` (search-snippet-based, not docs-page-confirmed — flagged as a risk below): `SessionStart` hook stdin includes a `source` field (`startup`/`resume`/`clear`/`compact`/`fork`), confirming `/clear` is independently detectable at the hook level, though this design doesn't end up needing it directly (see Decision 6's rejected alternative). No documented environment variable exposes the *current* session's own transcript file path to a Bash command outside a hook's stdin; the closest reliable alternative is resolving it by session-ID filename: `find "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects" -name "$CLAUDE_CODE_SESSION_ID.jsonl"`, which avoids reimplementing Claude Code's internal project-path-slug algorithm.
- The main spec already documents `crash-recovery-hook` as one of two pieces (alongside the `PreToolUse` write-guard hook) explicitly exempted from the version-marker/`SMW_VERSION` guarantee: it's a static, non-templated, machine-wide script, so editing its *content* needs no version bump — only a change to the fixed hook *entry* pointing at it would. `save-session-skill.md.template`, by contrast, is a per-project rendered, version-marked piece.

## Goals / Non-Goals

**Goals:**
- Correct the conceptual scope mismatch named above: move all live basic-memory note-content reading out of `check-drift.sh` into its own sourced file, mirroring the `migrations.sh` precedent, retroactively covering the prior change's additions as well as this change's new ones — with zero behavior change, purely an internal reorganization.
- Close the four specific, cheap gaps identified in the comparison (session-log bloat has no nudge at all; excerpt-only changes dilute the `DRIFT` signal; the excerpt carries no explicit freshness signal; the reminder reads as a directive rather than background context) without touching the binding decisions from the prior change (excerpt baked in at check-time, not live; bloat handled by nudge, not auto-pruning).
- Reuse existing mechanisms (`drift-warn`'s invocation point, `resolve_status_note_path()`'s glob pattern, `piece_status()`'s marker-extraction approach) rather than inventing parallel ones.
- Fix a redundancy identified mid-design (not in the original comparison): today, the cheap baked excerpt and the instruction to unconditionally call `search_notes`/`recent_activity` are both paid for every session in the common case where the model follows instructions, even though they largely cover the same ground (open items). Make the expensive call genuinely conditional on the cheap one being insufficient, rather than mandating both unconditionally.
- Fix a separate, user-raised issue in `crash-recovery-hook.sh`: replace pure session-ID-identity matching with a turns-since-last-save magnitude check, so a trivially small unsaved session (most commonly after `/clear`) doesn't trigger a reminder, while a large amount of unsaved work (whether from the same session continuing past an early save, or an entirely unsaved session) still does.

**Non-Goals:**
- Not moving any injected content to live-at-session-start computation — already rejected in the prior change's design.md, for the same reasons, which still hold.
- Not building an enforced/auto-pruning bloat mechanism. `save-session-maintenance` stays manual-trigger-only; this change only adds one more signal that nudges toward running it.
- Not attempting to byte-for-byte replicate `save-session`'s own wikilink-based active-log resolution in bash (see Decision 2 below for why, and what this uses instead).
- Not adding a deterministic `UserPromptSubmit` keyword hook to detect resume/status-request phrasing — considered and rejected; see Decision 5.
- Not changing anything about `migrations.sh` itself, or moving legacy-cleanup logic — this is a separate, parallel precedent, not something this change touches.
- Not adding an unconditional `/clear`-source exclusion to the crash-recovery hook — considered and rejected; see Decision 6. The user explicitly confirmed a large amount of work after `/clear` should still trigger the reminder, which only a magnitude-based check (not a source-based hard skip) gets right.
- Not adding a dedicated migration function for the marker-format change (bare session ID → `SESSION_ID:TURN_COUNT`) — handled as graceful fallback parsing (an old-format marker reads as turn-count `0`) rather than active cleanup; see Decision 6.

## Decisions

### 1. Extract note-content reading into a new sourced file, `memory.sh` — retroactively

A new file, `home/dot_claude/skills/setup-memory-workflow/scripts/memory.sh`, is sourced by `executable_check-drift.sh` the same way `migrations.sh` already is: no shebang, not executable, no argument-passing (its functions rely on `$PROJECT`/`$HOME` already set by the sourcing script), read-only, and never erroring — every function degrades to empty/no-op on any missing file or directory, exactly like the functions it's absorbing already do today.

**What moves, retroactively, with zero behavior change:** `resolve_status_note_path()`, `extract_open_excerpt()`, and the current-status-note-bloat portion of `cmd_drift_warn()`'s body (the `wc -c`/`wc -l`/`awk`-length checks and their threshold comparison) — all added by the prior change — move into `memory.sh` verbatim, or with only the minimal restructuring needed to split a check out of `cmd_drift_warn()`'s body into a standalone function.

**What's added fresh, directly in `memory.sh` rather than being written into `check-drift.sh` first:** `resolve_active_session_log_path()` and the new session-log-bloat check (Decision 2 below) — since the whole point of doing this split now is that new note-content logic should never have landed in `check-drift.sh` in the first place.

**What stays in `check-drift.sh`:** `render()` (template substitution is check-drift's actual job; it now calls `memory.sh`'s `extract_open_excerpt()` the same way it already calls into `migrations.sh`'s functions), `cmd_drift_warn()` as a thin orchestrator (keeps its own version-drift check — genuinely check-drift's concern — and calls out to `memory.sh`'s bloat-check functions for the rest, printing whatever lines they return), and every piece-status/rendering/drift-detection function untouched by this change (`piece_status()`, `canonical_hook_cmd()`, `cmd_check()`, `cmd_update()`, `cmd_apply()`).

**Why now, and why retroactive:** this change already adds a second instance of the same pattern (session-log-bloat, Decision 2) — doing that inside `check-drift.sh` again, on top of the prior change's current-status-note version, would cement the conflation rather than name and fix it. Splitting only the new addition and leaving the old one in place would leave `check-drift.sh` with the exact same scope problem, just smaller — not actually resolved. Since this is a pure internal reorganization (no externally observable behavior changes; nothing in the spec delta names a file path), there is no reason to defer the retroactive part to a separate change.

**Alternative considered — rename/re-scope `check-drift.sh` itself to formally include note-content reading as part of its job, instead of splitting:** rejected. That would permanently conflate two things that have genuinely different natures — comparing installed artifacts against deterministic canonical templates, versus reading live, evolving, user-authored content — under one name, for every future contributor to re-discover. Splitting them, the way `migrations.sh` already splits "legacy cleanup" out, keeps `check-drift.sh`'s actual job legible from its own name again.

**Consequence accepted:** two sourced files now exist, both pulled in near the top of `check-drift.sh`, and a reader needs to know the project's convention (sourced helper files, no shebang, not executable) to find where a given piece of logic lives. This is the same cost `migrations.sh` already carries today, not a new one.

### 2. Session-log bloat signal: identify the active log by file recency, not by re-parsing wikilinks

`cmd_drift_warn()`'s bloat-checking (now delegated to `memory.sh`, per Decision 1) gains a third independent signal (alongside the existing version-drift one in `check-drift.sh` and the current-status-note-bloat one already moved into `memory.sh`): it checks the **most recently modified file** under `$HOME/.local/share/basic-memory/$PROJECT/sessions/` against `save-session-maintenance`'s 300-line session-log rollover threshold, printing a suggestion when crossed.

**Why recency, not wikilink parsing:** `save-session`'s Step 1 resolution (most recent wikilink in the status note's Status Summary section, last wikilink if the entry has several) is model-interpreted prose, run with full MCP access to read and reason about note content. Reimplementing that same resolution logic in bash, with no MCP access, inside a hook that must never error, would be a second, independently-fallible parser for the exact kind of "small parser that could break on an unusual format" risk the prior change's design.md already flagged once (for `extract_open_excerpt()`'s Open-section parsing) and mitigated by keeping it narrow and bounded. Mtime-based identification is far simpler, needs no markdown-wikilink grammar, and matches reality: `save-session` appends to the active log every time it runs, so that file is reliably the most recently modified one in `sessions/` in practice.

**Alternative considered — parse the status note's wikilinks in bash, mirroring Step 1 exactly:** rejected. It would require a second awk/grep pass over the status note (on top of `extract_open_excerpt()`'s existing one) to find the Status Summary section, extract its most recent entry, find the last `[[...]]` wikilink in it, and resolve that link's title to an on-disk filename via the same Title-Case-glob technique `resolve_status_note_path()` already uses for the status note itself — all for a result this signal only needs as an advisory nudge, not an authoritative read. The precision isn't worth the added parser surface.

**Consequence accepted:** in the rare case where the most-recently-modified file in `sessions/` isn't actually the note `save-session` considers "active" (e.g. a status-archive-triage touched an older log more recently than the active one), the nudge could fire for, or fail to fire for, the wrong file. This is acceptable because the signal is advisory-only — worst case, a session-log rollover suggestion appears a session or two late or early, never anything destructive, and `/save-session-maintenance` itself (when actually invoked) still resolves the active log the authoritative way.

### 3. `STALE-EXCERPT` vs `DRIFT`: distinguish by comparing the embedded version marker, not the full string

`cmd_check()`'s `== SessionStart hook ==` block already extracts a `setup-memory-workflow-version:N` marker from file-based pieces via `piece_status()`. The hook command string carries the same marker (baked in by `render()`), so the same `grep -o 'setup-memory-workflow-version:[0-9]*' | grep -o '[0-9]*$'` extraction technique applies, this time against the string rather than a file's content. When the project-identity check (unchanged, still takes precedence per the existing "Identity mismatch always takes precedence" requirement) passes:
- marker differs from current `SMW_VERSION` → `DRIFT` (unchanged from today)
- marker matches, but the full string still differs from canonical → `STALE-EXCERPT` (new)
- marker matches and the full string matches → `UP-TO-DATE` (unchanged)

`cmd_update()`'s repair logic is **not** changed — it still unconditionally overwrites whenever the string differs (regardless of which of the two states caused the difference), since both are equally safe, consent-free repairs today. Only `cmd_check()`'s *reporting* category changes.

**Why this is sufficient, not a deeper redesign:** the only thing that can make the full command string differ while the version marker stays the same is the baked excerpt (and, after Decision 4 below, its capture date) — nothing else in the rendered template varies independently of `$PROJECT`/`$SMW_VERSION`. So marker-equality is already an exact, sufficient test for "only the excerpt-ish part changed," with no need to diff the two strings structurally.

**Alternative considered — stop reporting excerpt-only changes as any kind of drift at all:** rejected. The excerpt genuinely is stale relative to the live note once it differs, and losing that visibility would contradict the prior change's own design.md, which explicitly chose to keep staleness "reportable by the exact same mechanism that already exists for this piece" rather than inventing a silent one. This change keeps that reportability but gives it an honest, separate name instead of overloading `DRIFT`.

### 4. Capture-date stamp: computed once, by `render()`, only when the excerpt is non-empty

When `extract_open_excerpt()` returns non-empty content, `render()` appends the current date (`date '+%Y-%m-%d'`, computed once per render, not per-line) into the same header line that already introduces the excerpt block ("Open items from the status note (may be stale...)"). When the excerpt is empty, nothing changes — no date appears, preserving the prior change's byte-identical-to-the-no-excerpt-message guarantee for that case.

**Why here, not as a separate placeholder:** the date is only ever meaningful alongside a non-empty excerpt (a date on an absent excerpt would be confusing, implying something was checked and found nothing, when really nothing was ever attempted to be shown). Folding it into the existing conditional header, rather than adding a fourth `__EXCERPT_DATE__`-style placeholder with its own empty-string handling, avoids a second independent "is this empty" branch to keep in sync with the first.

### 5. Reminder framing: make retrieval genuinely lazy, and name the phrasing that overrides it

Three wording changes to `hook-message.txt.template`, bundled together since they all touch the same instruction text:

**a) Background-context framing.** The instruction text changes from an imperative ("Your FIRST action this session...") to language that frames the whole reminder — base instruction and excerpt alike — as background context the model should weigh against, not place ahead of, the user's actual current request.

**b) Conditional retrieval, not unconditional.** The instruction to call `search_notes`/`recent_activity` changes from a mandatory first action to something conditioned explicitly on the excerpt (plus its capture date, Decision 4) being insufficient — e.g. "the Open items above are a snapshot as of \<date\>; call `search_notes`/`recent_activity` yourself only if you need more than that (older context, a different note, or the excerpt looks stale or missing)." This is the actual fix for the redundancy named in Goals above: today the cheap excerpt and the expensive MCP round-trip are both paid for unconditionally whenever the model follows instructions, even though they mostly cover the same ground. Conditioning the expensive call on insufficiency removes that double payment in the common case.

**c) Named override phrasing.** Explicit guidance naming the kind of user phrasing that should override (b)'s "only if insufficient" default and always trigger the real call regardless of how fresh the excerpt looks — direct resume/status-request language such as "what's the current status," "where did we leave off," "let's resume/continue." This is model-judgment only, no new mechanism: the model already sees the user's literal first message in the same turn it sees this reminder, so detecting the phrasing needs no runtime hook — it's purely an instruction refinement.

No placeholder, substitution, or script logic changes anywhere in this decision; it's a `SMW_VERSION`-bumping content edit to the template file, same category of change as any prior wording revision to that asset.

**Why (c) needs no new hook:** considered and rejected a `UserPromptSubmit`-based keyword hook that would grep the user's literal message and inject a stronger reminder only on a match. Rejected for the same reason the skill's own `v8` changelog entry gives for moving off `UserPromptSubmit` in the first place: a reminder injected alongside the user's own message competes with it for attention and loses. A resume/status-request message is exactly the case where that competition matters least (the user's own message already asks for memory context, so a memory reminder would reinforce it, not compete) — but `SessionStart` fires before that message exists, so no hook at that point can see the message text to decide whether to escalate. The only thing that reliably sees both the reminder and the user's message in time to act on either is the model itself, at inference time, which is what (c) relies on instead.

**Consequence accepted:** (b) and (c) are both soft — the model could misjudge the excerpt as sufficient when it isn't, or fail to recognize an unusually-phrased resume request. This doesn't weaken an existing guarantee: the prior "call this unconditionally" wording was never actually enforced by anything other than the model choosing to comply, so there was no hard guarantee to begin with — only the token cost of asking unconditionally, which (b) is specifically removing.

**Why now, bundled with the other decisions:** on its own, (a)/(b)/(c) wouldn't justify a version bump and a round of `update`s across every installed project. Bundling them with the functional changes in Decisions 2-4 means projects already due for an `update` get this wording improvement in the same pass, rather than waiting for some unrelated future bump to justify it alone.

### 6. Crash-recovery: replace session-identity matching with a turns-since-last-save magnitude threshold

`crash-recovery-hook.sh` and `save-session`'s three marker-writing spots both change, together:

**Marker format.** `.claude/.last-saved-session` changes from a bare `$CLAUDE_CODE_SESSION_ID` to `$CLAUDE_CODE_SESSION_ID:$TURN_COUNT`, where `$TURN_COUNT` is the number of real user turns in the current transcript at the moment of writing, via the verified filter: resolve the transcript by session-ID filename (`find "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects" -name "$CLAUDE_CODE_SESSION_ID.jsonl"`, avoiding any project-path-slug reimplementation), then `jq -c 'select(.type=="user" and (.toolUseResult // null)==null and (.isMeta // false)==false)' "$TRANSCRIPT" | wc -l`. All three spots in `save-session-skill.md.template` (Step 0's two skip/no-op paths, and "On success") get this same one-liner in place of today's bare `echo "$CLAUDE_CODE_SESSION_ID" > .claude/.last-saved-session`.

**Comparison logic.** `crash-recovery-hook.sh` already resolves the most recently modified prior transcript (`$LATEST_PRIOR`) and its session ID (`$PRIOR_SESSION_ID`) via `transcript_path` from its own hook stdin — no slug problem here, since the hook payload gives the real path directly. It now also counts `$LATEST_PRIOR`'s own total real-user-turns via the same jq filter, and computes "unsaved turns" as: that total minus the marker's recorded `$TURN_COUNT` if `$PRIOR_SESSION_ID` matches the marker's session ID (a session that saved early then kept going), or the full total if it doesn't (a session, however it started, that was never saved at all — covering both the `/clear` case and a plain unsaved session). The reminder fires only when unsaved turns exceeds a new named constant, `UNSAVED_TURN_THRESHOLD=5`, placed at the top of the script next to its other constants — same "easy to bump later" ergonomics as `OPEN_EXCERPT_MAX_LINES` in `check-drift.sh`.

**Why a magnitude threshold, not a `/clear`-source exclusion:** considered and rejected detecting `/clear` directly via the hook's `source` field and unconditionally skipping the reminder whenever the current session started that way. Rejected because the user explicitly confirmed: if more than the threshold's worth of turns happen after a `/clear` before the session ends unsaved, they still want the reminder — "that counts as a new session and I probably want to be saving." A hard source-based skip would wrongly suppress exactly that case; a magnitude check gets both halves right with one rule, and naturally also fixes the `/clear` false-positive, since `/clear`-started sessions that end quickly (the common case prompting this request) fall under the threshold on their own.

**Why old-format markers degrade to turn-count `0`, not a migration:** an old bare-session-ID marker simply has no `:turn_count` to parse. Treating the missing part as `0` is the same "degrade silently, never error" pattern every other piece of this skill already follows, and self-heals the moment any one of the three marker-writing spots runs again. The cost — one possible spurious reminder, immediately after upgrading, for a session that's already fully saved — is strictly smaller than inventing an active migration step for a one-time, self-correcting gap.

**Deployment asymmetry, called out explicitly:** `crash-recovery-hook.sh`'s own logic change needs no `SMW_VERSION` bump and no per-project `update` — it's the static, machine-wide-deployed script the main spec already exempts from version-marker tracking, so the fix is live everywhere the moment `chezmoi apply` runs on the machine. `save-session-skill.md.template`'s marker-writing one-liners, by contrast, are part of a per-project rendered, version-marked piece, so *that* half rides along with this change's shared `SMW_VERSION` bump and needs `check-drift.sh update` per project, same as everything else in this change.

**Consequence accepted:** the `find`-by-session-ID-filename approach searches the whole `~/.claude/projects/` tree rather than a known subdirectory, since reconstructing the project-slug directory name reliably wasn't achievable with confidence (see Context). This is a cheap, bounded filename search (one exact match expected, given session IDs are UUIDs), not a performance concern.

## Risks / Trade-offs

- **[Risk] The `memory.sh` extraction (Decision 1) is a pure refactor touching already-shipped code — a mechanical mistake in the move could silently change behavior (e.g. a dropped `local` keyword changing a variable's scope).** → Mitigation: every moved function is covered by the prior change's existing fixture tests; those same fixtures are re-run against the post-move code as a regression check (see tasks.md) before any new functionality is added on top.
- **[Risk] Mtime-based active-log identification (Decision 2) can point at the wrong file in edge cases.** → Mitigation: accepted explicitly; advisory-only signal, no auto-remediation, `save-session-maintenance` itself still resolves the active log authoritatively when actually invoked.
- **[Risk] `STALE-EXCERPT` is a new state string that `check-drift.sh check`'s callers (currently just the model reading its output) need to recognize as "safe to `update`," same as `DRIFT`.** → Mitigation: `cmd_update()`'s repair logic doesn't change at all — both states repair identically — so the only new thing to learn is a label, not a new remediation path.
- **[Trade-off] The capture-date stamp (Decision 4) means the baked excerpt's rendered text changes at least once per calendar day it's non-empty, even with no change to the underlying Open items — which, combined with Decision 3, means `STALE-EXCERPT` will now fire once per day by design whenever the excerpt is non-empty and `check` hasn't been re-run that day.** → Accepted: this is the intended behavior, not a bug — a dated excerpt that silently stopped updating its date would be a worse, misleading signal than one that visibly asks for a refresh. `STALE-EXCERPT`'s whole purpose (Decision 3) is to make exactly this kind of change reportable without diluting real template drift.
- **[Risk] The turn-counting jq filter (Decision 6) was verified against this project's own real transcripts, but Claude Code's transcript schema (`type`, `isMeta`, `toolUseResult` fields) is an internal format with no stability guarantee across Claude Code versions — the same class of risk the main spec's own "Comparative lessons" doc already names for this skill's hook scripts generally.** → Mitigation: the filter degrades safely, not loudly, if the schema shifts — an unrecognized `type` value simply isn't counted as a turn (undercounting, not an error), so the worst case is a missed reminder, not a crash or a wrong repair. Re-verify the filter against a real transcript whenever a Claude Code upgrade is suspected of changing transcript shape.
- **[Risk] The `source`-field and transcript-path-env-var facts (Decision 6's Context) came from `claude-code-guide`'s search-snippet-based research, not a directly fetched, confirmed docs page (`WebFetch` was unavailable both times).** → Mitigation: this design doesn't end up depending on the `source` field at all (the magnitude check subsumes it — see Decision 6's rejected alternative), and the transcript-path workaround (find by session-ID filename) doesn't depend on the unconfirmed env var either, so the design is robust to that specific fact turning out to be wrong. Re-verify by logging real hook stdin once during implementation (task-level verification) rather than trusting the search summary alone.

## Migration Plan

- Do the `memory.sh` extraction (Decision 1) first, as a standalone, behavior-preserving step, verified against existing fixtures before any new logic (Decisions 2-5) is added on top of it.
- Bump `SMW_VERSION` in `executable_check-drift.sh` once, covering all functional and wording changes together — same pattern as every prior bump. The `memory.sh` extraction itself needs no version bump on its own (no observable behavior changes), but ships in the same commit as the bump for the functional changes.
- Existing installs: the session-log bloat signal (Decision 2) and the `STALE-EXCERPT`/`DRIFT` split (Decision 3) both live in global, non-per-project-rendered script logic (now split across `check-drift.sh` and `memory.sh`, both deployed machine-wide the same way `migrations.sh` already is), so they take effect immediately on the next session start with no `update` needed — same as the prior change's current-status-note-bloat signal. The capture-date stamp (Decision 4) and reworded framing (Decision 5) are per-project rendered template content, so existing installs report drift (as `STALE-EXCERPT` once the date differs, or `DRIFT` from the version bump itself) and need `check-drift.sh update` to pick them up, consistent with every prior bump.
- `crash-recovery-hook.sh`'s turn-count comparison logic (Decision 6) needs no `SMW_VERSION` bump and no per-project `update` — it's deployed machine-wide, non-templated, and takes effect the moment `chezmoi apply` runs. `save-session-skill.md.template`'s marker-writing one-liners (also part of Decision 6) are per-project rendered content, so that half does ride along with the shared `SMW_VERSION` bump and needs `update` per project, same as Decisions 4-5.
- No rollback mechanism beyond the existing one: `git revert`, bump `SMW_VERSION` again, installed projects pick up the reverted template on their next `update` (for the rendered pieces) or the next `chezmoi apply` (for `crash-recovery-hook.sh` itself).
