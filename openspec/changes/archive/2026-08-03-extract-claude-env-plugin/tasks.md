**Bug found and fixed (2026-08-03)**: the baseline-capture code at `zsh-claude-env.plugin.zsh:138-143` ran `local REPLY` at the plugin's *file top level* (not inside any function). This was safe on a normal oh-my-zsh load, because oh-my-zsh's own loader (`_omz_source` in `oh-my-zsh.sh`) sources plugin files from inside a function, so `local` scoped correctly there. But the plugin's README also documents a **standalone** install path (`source ~/work/zsh-claude-env/zsh-claude-env.plugin.zsh` directly in `.zshrc`, no oh-my-zsh required) — sourced that way, the code ran at `.zshrc`'s own top level, where zsh's `local` degrades to plain `typeset`. Reproduced directly: after one `source` (which set a now-global `REPLY`), a second `source` of the same file — e.g. any ordinary `source ~/.zshrc` to reload config — had zsh's `typeset REPLY` (no `=value` on that line) print the *already-set* variable as `REPLY=<value>` straight to the terminal. Confirmed the underlying mechanism in isolation from this plugin: `zsh -f -c 'local REPLY; REPLY=foo; local REPLY'` → prints `REPLY=foo`. Two other top-level `local` declarations in the same file (`_claude_env_dir`, `_claude_env_n`) were checked too — not affected, because the file already `unset`s both right after their loops, so no stale value survives to a later `typeset` call. Fixed by wrapping the baseline-capture block in an anonymous function (`() { local REPLY; ...; }`), giving `local` a real scope regardless of caller context. Re-ran the full 2.1-2.7 suite against the fixed plugin: all still pass, leak confirmed gone. Committed `668833f` and pushed to `main` on 2026-08-03 with explicit user confirmation for both the commit and the push, per standing git-workflow practice; tagged and pushed as `v0.2.1`.
