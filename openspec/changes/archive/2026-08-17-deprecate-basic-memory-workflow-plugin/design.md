## Context

See `proposal.md` - Why for motivation. Three concrete, previously-documented facts shape this design directly rather than being re-derived from first principles:

1. **The 2026-07-15 chezmoi-dotfiles/chezmoi basic-memory project mixup** is the precedent behind keeping an override escape hatch for project identity rather than trusting directory-basename derivation unconditionally. This was already the reasoning behind `.claude/basic-memory-project.txt` when it was introduced during the plugin's runtime-resolution design — this change carries that file forward, just consulted at apply-time instead of runtime.
2. **The original v8 skill's actual bug**, per its own `CHANGELOG.md` and the plugin-conversion's `proposal.md`: a project's installed `save-session/SKILL.md` sat stuck at `version:1`/`2` while canonical had moved to `6`, because the only repair path (`check-drift.sh apply <piece>`) required a human to notice drift was reported and then explicitly confirm each piece. The bug was "repair requires remembering and confirming," not "copies exist."
3. **OpenSpec's `openspec init`/`update`** (`src/core/init.ts`, `src/core/update.ts`, `src/core/shared/tool-detection.ts` in `~/work/OpenSpec`, examined via a dedicated research pass) demonstrates a stronger version of the same copy-based shape already in production elsewhere: a `generatedBy` version marker per installed file, and an `update` command that computes exactly which files are stale and unconditionally overwrites them — no per-piece confirmation. Their own original design doc for that command states the guiding principle plainly: *"No version tracking - always update when commanded... Dead simple... Fast: No version checks, minimal parsing."* Their copy-vs-shared-plugin choice itself has no documented rationale (plugin systems are simply absent from their codebase) and is best read as a consequence of targeting 30+ heterogeneous AI tools, not a lesson transferable to a Claude-Code-only skill — the technique worth borrowing is the marker-plus-unconditional-repair-command, not "copying is inherently better than a shared plugin."

Also relevant: the plugin's own `installed_plugins.json` records confirm its cache is commit-SHA-pinned, materialized at install time by `claude plugin install`, and does not live-resolve from source — `claude plugin update` was found (both in the original design's Operational Note and re-confirmed during this investigation) to silently no-op against a dirty working tree, with `uninstall`+`install` as the only reliable refresh path. This is normal, expected package-manager behavior, not a bug — but it means the plugin never actually delivered a *simpler* update story than a well-built copy-based one; it delivered a different one, with its own footgun (no `needsUpdate` signal surfaced anywhere, unlike OpenSpec's `generatedBy` check).

**This isn't hypothetical — a live install is already stale.** A discovery pass across every `CLAUDE_CONFIG_DIR` this user actually uses (`~/.claude`, `~/.claude-bedrock`, `~/.claude-personal`, `~/.claude-work` — plugin installs are per-persona and not shared, unlike the `skills/` directory, which is symlinked identically to `~/.claude/skills` from all three active personas) found `basic-memory-workflow`'s install under `.claude-work` for this chezmoi repo pinned to commit `ffa505790a48` (2026-08-06), never updated since, with six commits since then touching `plugins/basic-memory-workflow/` that never reached it — including a real data-loss fix (`b0bf2c1`, "sync-memory cursor data-loss and mid-session registration gaps") and a registration-gap fix (`531d07f`). The cached directory `installed_plugins.json` points to for that install no longer even exists on disk — a dangling record. This is the precise failure mode described in point 2 above, recurring one layer up, on this machine, right now.

## Goals / Non-Goals

**Goals:**
- Eliminate the specific failure mode observed in practice: `$PROJECT` resolution is skippable because it's an instruction the model can rationalize away, not a fact already sitting in the file.
- Preserve the plugin era's one genuine improvement — the override-file escape hatch — by relocating it to apply-time rather than discarding it.
- Replace `check-drift.sh`'s detect-only repair loop with an unconditional-overwrite `update` command for the risk class where that's safe (version content drift), while keeping the identity-change case (`NAME-MISMATCH`) exactly as confirm-gated as it's always been.
- Leave `save-session`/`sync-memory` runtime behavior identical from a user's perspective — this is a distribution change, not a feature change (mirroring the original conversion's own stated goal).

**Non-Goals:**
- Rebuilding general multi-plugin marketplace tooling, auditing other plugins' scope hygiene, or solving plugin packaging for other dotfiles-repo tooling — all out of scope, matching the original conversion's non-goals in kind.
- Any change to how basic-memory itself is installed or how its MCP server is registered globally.
- Restoring the plugin's per-invocation idempotent registration check inside `save-session`/`sync-memory` — deliberately not carried back; see Decisions.

## Decisions

**`$PROJECT` resolution moves back to apply-time, but keeps the override file.** Order: `<project-root>/.claude/basic-memory-project.txt` (if present, non-blank) → else `basename` of `git rev-parse --show-toplevel`. This single derivation point feeds every `render()` call in `check-drift.sh` (skill content, hook string, `sync-memory.py`) exactly as `$PROJECT` already does today — only what populates the variable changes. No runtime script ships in the deployed skill files anymore; the resolution logic lives once, in `check-drift.sh`, run only when `check`/`update`/`apply` are invoked.

**`update` is new: unconditional overwrite for version drift only.** Modeled directly on `openspec update`'s `needsUpdate`-then-overwrite pattern. `check`'s existing marker comparison already computes exactly this information (`marker < SMW_VERSION` and `name_match`) — `update` reuses that computation, then calls `apply_templated_file()` (already exists, unchanged) for every piece where only the version marker is stale, with no per-piece confirmation prompt. This is safe specifically because version drift only ever means "canonical changed and this file hasn't caught up" — the resulting content is always meant to be identical to what's already the canonical source of truth.

**`NAME-MISMATCH` stays confirm-gated, deliberately excluded from `update`.** An identity change is a different risk category from a content change — it means either the override file was edited, or an un-overridden project's directory was renamed, and either could be intentional or a mistake. `update` explicitly skips any piece in this state and reports what it skipped; only the existing `apply <piece>` path (unchanged mechanism, unchanged discipline) repairs it, and `SKILL.md`'s instructions require showing the user the old-vs-new identity before that invocation — never silently.

**Registration reverts to v8's original apply-time-only behavior; the plugin's per-invocation check is not carried back.** The plugin moved registration into an idempotent check at the top of every `save-session`/`sync-memory` run specifically because removing the installer skill removed the one natural place for it to live. Restoring the skill restores that natural home, so the added redundancy is no longer buying anything — one apply-time `basic-memory project add` (already idempotent, already how v8 worked) is sufficient again.

**Considered and rejected: symlinking shared instruction content instead of copying it.** Raised during exploration as a way to make the bulk of `SKILL.md` (the parts that don't need `$PROJECT` substitution) literally undriftable by construction. Rejected for two reasons: (1) it reintroduces exactly the "residual staleness risk requiring bespoke tooling" pattern already rejected earlier in this same exploration for the plugin's cache-pinning — a written copy plus a reliable `update` command is the same acceptable shape either way, and treating the two inconsistently isn't defensible; (2) it adds a real, unverified platform-support question (does Claude Code resolve symlinked skill resources) and a portability problem (an absolute-path symlink checked into a shared/team project's repo breaks for every other clone) for a benefit `update` already provides more simply.

**Version marker continues past v8 (next value: v9); `CHANGELOG.md` gets a new entry** documenting the override-file-at-apply-time change, the `update` command, and the registration-timing reversion, in the same style as the existing v8 entry.

## Risks / Trade-offs

- **[Risk]** `update`'s unconditional overwrite removes the per-piece confirmation step version-drift repairs used to have. → **Mitigation**: scoped deliberately to version-content drift only, which is by definition "this file should already look like canonical" — there is nothing for a human to weigh per-piece the way there is for an identity change. `NAME-MISMATCH` keeps the old confirm-gated path entirely.
- **[Risk]** The override file itself can go stale (a rename happens, nobody updates it) with no automatic staleness detection. → **Mitigation**: unchanged from the plugin-era assessment of the same risk — explicitly out of scope, a rare manually-maintained escape hatch, not the default path.
- **[Risk]** Removing the plugin's `user`-scope enablement in `~/.claude-personal/settings.json` will silently stop the workflow in any project that was relying on it without a deliberate local opt-in. → **Mitigation**: this is a correction, not a regression — the plugin's own spec requires per-project explicit opt-in, so any project silently depending on the global entry was already out of spec. Migration Plan requires identifying those projects before removing the global entry, not after.
- **[Risk, resolved during design]** External targets beyond this repo might not be re-discoverable. → **Resolution**: a discovery pass across all four `CLAUDE_CONFIG_DIR` personas (`claude plugin list --json` under each) found the complete, confirmed real-install set — see Migration Plan step 4. Two targets beyond `chezmoi` itself: `WES.ViewPoint.ExternalIntegration.FulcrumAppAPI` (the original conversion's known target, confirmed still relevant) and `WES.ViewPoint.CommonMicro.API` (not previously documented anywhere, confirmed active). Both are explicitly in scope per user confirmation.
- **[Risk]** Coexistence window: while both the enhanced skill and the plugin are present, a project could end up with both active, producing duplicate `SessionStart` reminders or duplicate `save-session`/`sync-memory` skills. → **Mitigation**: migrate one project at a time — enable the skill and disable the plugin for that project in the same step, not as separate passes, mirroring how `migrate-to-plugin.sh` originally handled the reverse direction.

## Migration Plan

1. Enhance `home/dot_claude/skills/setup-memory-workflow/` in place per the Decisions above (override-file resolution, `update` subcommand, split DRIFT/NAME-MISMATCH reporting, apply-time-only registration, version bump, `CHANGELOG.md` entry). `plugins/basic-memory-workflow/` stays untouched, coexisting — same rollout discipline the original conversion used, in reverse. Since `~/.claude-bedrock/skills`, `~/.claude-personal/skills`, and `~/.claude-work/skills` are all symlinked to the same `~/.claude/skills` (confirmed during discovery), chezmoi deploying the enhanced skill once makes it available under every persona with no extra fanout needed — unlike plugin installs, which are per-persona and not shared.

2. **Confirmed real-install inventory** (via `claude plugin list --json` under each of the four `CLAUDE_CONFIG_DIR` personas — `~/.claude` has no `chezmoi-personal` marketplace registered and zero installs, effectively unused for this workflow):

   | Persona | Project | Scope | Notes |
   |---|---|---|---|
   | `.claude-personal` | `chezmoi` | local | |
   | `.claude-personal` | *(none — global)* | **user** | active in every project under this persona; no per-project record to enumerate against |
   | `.claude-work` | `chezmoi` | local | **stale**: pinned to `ffa505790a48`, 6 commits behind, cache directory no longer exists on disk |
   | `.claude-bedrock` | `WES.ViewPoint.CommonMicro.API` | local | confirmed active, in scope |
   | `.claude-bedrock` | `WES.ViewPoint.ExternalIntegration.FulcrumAppAPI` | **project** | confirmed in scope — `project` scope means this lives in that repo's committed `.claude/settings.json`, visible to any other contributor; worth a heads-up to the team there before removal, not just a local config edit |

3. Migrate `chezmoi` first, as this repo is worked in directly: run the enhanced skill's `check` then `update`/`apply` against it; verify `save-session`, `sync-memory`, and the `SessionStart` hook behave identically to the plugin version currently does. Then disable/uninstall `basic-memory-workflow@chezmoi-personal` at `--scope local` under **both** `.claude-personal` and `.claude-work` (two separate install records for the same project — plugin state doesn't share across personas even though the skill files now do), removing the corresponding `enabledPlugins` entries.
4. Migrate `WES.ViewPoint.CommonMicro.API`: run the enhanced skill's `check`/`apply` there under `.claude-bedrock`, then disable/uninstall the plugin at `--scope local`.
5. Migrate `WES.ViewPoint.ExternalIntegration.FulcrumAppAPI`: run the enhanced skill's `check`/`apply` there under `.claude-bedrock`, then remove the plugin entry at `--scope project` — this edits that repo's committed `.claude/settings.json`, so it should land as its own reviewable change in that repo rather than a silent local edit.
6. Remove the `user`-scope enablement from `~/.claude-personal/settings.json` only after steps 3-5 are confirmed working — this is the one entry with no enumerable list of affected projects (it covers every project opened under that persona, not just the ones with their own install record); if some other project's reminder silently disappears afterward, that's the signal to give it its own deliberate local install via the enhanced skill, which is the correct end state anyway.
7. Only once every target in the table above is confirmed working on the enhanced skill: remove `.claude-plugin/marketplace.json`'s `basic-memory-workflow` entry and delete `plugins/basic-memory-workflow/` in full.

**Rollback**: until step 7, the plugin is untouched and fully functional — any problem found in steps 1-6 is resolved by simply not proceeding further, the same rollback safety property the original conversion's design relied on. After step 7, rollback means restoring the deleted plugin directory and marketplace entry from git history.
