## Why

`basic-memory-workflow` (the Claude Code plugin that replaced `setup-memory-workflow` on 2026-08-06) eliminated the bug it was built to fix — per-project copies silently drifting from canonical because nothing forced them to update — but it did so by moving `$PROJECT` resolution from a install-time constant to a runtime script call the model must remember to make. In practice the model routinely skips that call: the plugin's own `SessionStart` hook already announces the project name in prose before `save-session`/`sync-memory` ever run, so re-deriving it a second time reads as redundant even though it's the only thing that also re-applies the `.claude/basic-memory-project.txt` override and (mid-session-enable cases aside) re-confirms registration. Separately, the plugin's install/update model turned out weaker than assumed: `claude plugin update` compares a cached commit SHA, not live content, and silently no-ops against a dirty working tree (confirmed via the original design's own Operational Note); the only reliable refresh path is uninstall-then-reinstall. And auditing this repo's actual install state during this investigation surfaced that `basic-memory-workflow@chezmoi-personal` is currently enabled at Claude Code's `user` scope in `~/.claude-personal/settings.json` — active in every project on this machine, not the per-project opt-in the plugin's own spec requires.

Research into OpenSpec's own `openspec init`/`update` (a live copy-based installer, examined specifically as prior art) showed a stronger version of the *original* skill's approach was available all along: static, non-templated-at-runtime content, a version marker in each installed file, and an `update` command that unconditionally overwrites anything stale — no per-piece confirmation dance, no runtime resolution to skip. Combining that pattern with the one genuine improvement the plugin era produced — the `.claude/basic-memory-project.txt` override escape hatch, added in direct response to the 2026-07-15 chezmoi-dotfiles/chezmoi basic-memory project mixup — gives a design that is simpler than the plugin, safer than the original v8 skill, and closes the actual bug (skippable identity resolution) rather than trading it for a different one (invisible cache staleness).

## What Changes

- `home/dot_claude/skills/setup-memory-workflow/` (currently present but inert — restored for reference on 2026-08-17, not wired into anything) becomes the actively maintained mechanism again. Its `check-drift.sh` gains:
  - `$PROJECT` resolution order at apply-time: `<project-root>/.claude/basic-memory-project.txt` (if present and non-blank) → else `basename` of `git rev-parse --show-toplevel`. This is new relative to the original v8 skill — v8 only ever did the bare `basename` derivation; the override file was invented later, during the plugin's runtime-resolution design, and is being carried back rather than dropped.
  - A new `update` subcommand: unconditionally re-renders and overwrites every installed piece currently flagged as version DRIFT (OpenSpec `openspec update` semantics — no per-piece confirmation, since version-content drift is always safe to reconcile to canonical).
  - `check`'s DRIFT reporting splits into two categories: version drift (safe, fixable by `update`) and `NAME-MISMATCH` (an identity change — override file edited, or an un-overridden project renamed) — which stays confirm-gated via the existing `apply <piece>` path exactly as today, never auto-repaired.
  - Registration (`basic-memory project add ...`) reverts to being purely a `check`/apply-time action, as it already was in v8 — the plugin's move to an additional idempotent per-invocation check inside `save-session`/`sync-memory` is not carried back, since removing the plugin restores the one natural place (the skill's own apply step) for this to live.
  - Version marker bumps past v8 (next value, e.g. `v9`); `CHANGELOG.md` gains an entry describing the above.
- `home/dot_claude/skills/setup-memory-workflow/assets/*.template` and `scripts/sync-memory.py.template` keep their existing `__PROJECT__`/`__SMW_VERSION__` substitution mechanism — the source of the `$PROJECT` value changes (override-file-aware now), not the rendering mechanism itself. **Their content also needs updating**, separately from that: the templates were last touched at v8, before the plugin era, and four real plugin-only commits since then changed actual behavior that never made it back into these templates — `28dc2cc` (session-log auto-rollover past 300 lines, currently absent from the v8 template entirely), `b0bf2c1` (sync-memory cursor data-loss and mid-session registration-gap fixes, spanning `sync-memory.py` and both `SKILL.md` files), and `531d07f` (bootstrap-on-first-`SessionStart` handling). "Leave runtime behavior identical from a user's perspective" (see design.md Goals) means identical to *current* behavior, so these need porting forward into the templates, not left behind as a side effect of reverting distribution mechanism.
- **BREAKING**: `plugins/basic-memory-workflow/` and its `.claude-plugin/marketplace.json` entry are removed once migration is verified (see design.md's Migration Plan) — coexisting with the enhanced skill until then, matching the original conversion's own "delete last, gated on verification" discipline in reverse. The shared `chezmoi-personal` marketplace itself, and every other plugin registered in it (atlassian, cloudflare, code-quality, systems-design, aws-local-dev, browser-tools, openspec-dashboard, serena), is untouched.
- **Externally affected, one-time cleanup**: `basic-memory-workflow@chezmoi-personal`'s `user`-scope enablement in `~/.claude-personal/settings.json` is removed. Any project that was silently relying on that global enablement (not a deliberate per-project opt-in) needs the enhanced skill's `check`/apply run against it explicitly afterward, to restore the workflow — this is a correction of drift from the plugin's own documented per-project-opt-in requirement, not a new capability.
- `save-session`/`sync-memory` runtime *behavior* — what gets written, the session-log-vs-status-note split, `sync-memory`'s dual-mode/cursor-tracking — is unchanged. This is a redistribution-mechanism reversal, not a feature change, same framing the original plugin-conversion proposal used.

## Capabilities

### New Capabilities
(none)

### Modified Capabilities
- `setup-memory-workflow`: reverts from plugin distribution (single shared copy, runtime identity resolution, per-invocation registration checks) back to install-time-copy-with-drift-checking, enhanced with an override-file-aware identity resolution (new relative to the original v8 shape) and an unconditional-overwrite `update` command for version drift (new, OpenSpec-inspired) while keeping `NAME-MISMATCH` confirm-gated (unchanged discipline). Essentially every requirement describing *how* is rewritten again; the capability's purpose is unchanged.
- `sync-memory`: the plugin-era requirement "project identity resolved at runtime via `resolve-project-name.sh`" is reversed back to install/apply-time baking — with the override-file resolution now folded into that apply-time step instead of dropped. The separate, unrelated requirement that the *filesystem* project root (for `.specstory/history` and cursor-state lookup) stays dynamically resolved via `git rev-parse --show-toplevel` is unchanged either way — that was never an identity question.
- `claude-plugin-marketplace`: narrow modification — the `basic-memory-workflow` entry is removed from `.claude-plugin/marketplace.json` once migration completes. The capability itself (local marketplace registration, third-party-source plugin entries, non-templated `plugins/` content) is unchanged and continues serving every other plugin registered in it.

## Impact

- **Affected code**: `home/dot_claude/skills/setup-memory-workflow/` (`check-drift.sh`, `CHANGELOG.md`, and the `assets/`/`scripts/` templates — enhanced in place); `plugins/basic-memory-workflow/` and its `.claude-plugin/marketplace.json` entry (removed once migration is verified); this repo's own `.claude/settings.local.json` (plugin `enabledPlugins` entry removed, legacy-cleanup-then-re-apply via the skill's own migration path).
- **Externally affected**: `~/.claude-personal/settings.json` (`user`-scope plugin enablement removed — a different config file than anything chezmoi manages, on this machine only). Confirmed real installs, discovered by checking `claude plugin list --json` under every `CLAUDE_CONFIG_DIR` persona (`.claude`, `.claude-bedrock`, `.claude-personal`, `.claude-work`): `WES.ViewPoint.CommonMicro.API` (`.claude-bedrock`, local scope, confirmed active) and `WES.ViewPoint.ExternalIntegration.FulcrumAppAPI` (`.claude-bedrock`, **project** scope — committed to that repo's `.claude/settings.json`, so its removal is visible to any other contributor there, not just a local edit) — both confirmed in scope. `chezmoi` itself is installed twice, once each under `.claude-personal` and `.claude-work` (plugin state is per-persona, unlike the shared `skills/` directory); the `.claude-work` install was found stale — pinned to commit `ffa505790a48`, six commits and a real data-loss fix behind, with a dangling cache directory — live evidence of the exact failure mode this change addresses. See design.md's Migration Plan for the full confirmed inventory.
- **Not touched**: basic-memory's global MCP server registration (script-38, `packages.yaml`'s `mcp_servers` entry — orthogonal to this change, same as it was orthogonal to the original conversion); `save-session`/`sync-memory` runtime behavior; the `basic-memory` tool installation bootstrap (`uv tool install basic-memory`, still a manual prerequisite); the `chezmoi-personal` marketplace infrastructure and every plugin in it other than `basic-memory-workflow`.
- **Tags affected**: none — `home/dot_claude/skills/setup-memory-workflow/` deploys via chezmoi's ordinary dotfile management, the same untagged mechanism it used before the plugin conversion; no package/tag-gating changes are involved.
- **Security**: no secrets involved. The migration path reuses `check-drift.sh`'s existing never-silently-overwrite discipline (report first, act only on explicit confirmation) for anything identity-related; version-drift auto-repair via `update` is safe to run unconditionally because it only ever reconciles managed files to canonical content, never touches user data.

## Non-goals

- Not removing the `claude-plugin-marketplace` capability or disturbing any other plugin registered in `chezmoi-personal` — this is scoped to `basic-memory-workflow` alone.
- Not changing what `save-session`/`sync-memory` actually write to basic-memory, or their command-line behavior.
- Not building a generic, reusable "versioned config-file installer" framework — the `update`/`NAME-MISMATCH` split stays scoped to this one skill, matching the original conversion's own non-goal about not building general multi-plugin tooling.
- Not auditing or fixing other plugins' scope hygiene in `~/.claude-personal/settings.json` — the `user`-scope leak found for `basic-memory-workflow` is addressed because this change touches that plugin directly; it is not a general plugin-scope audit.
