# Design

## Context

See `proposal.md` - Why for the three findings this addresses. Three separate mechanisms, one design doc because all three are small, security-motivated fixes to already-shipped capabilities reviewed together by the same Codex pass, and the fixes don't compete for the same files.

**Finding 1 groundwork**: `chezmoi execute-template` confirms the exact defect — `{{ "a$(echo b)c" | quote }}` renders `"a$(echo b)c"` (double-quoted, `$()` untouched — expands when sourced/executed), while `{{ "a$(echo b)c" | shellQuote }}` renders `'a$(echo b)c'` (single-quoted, inert). `quote` is chezmoi's JSON-style quoting function; it is correct for the templates in this repo that render into JSON/TOML data (`home/.chezmoi.toml.tmpl`, the `dot_claude-plugin/*.json.tmpl` files, `gcp-oauth.keys.json.tmpl`) and wrong for the ones that render into a shell-variable assignment or shell command argument.

**Finding 2 groundwork**: `home/private_dot_cloudflared/private_cert.pem.tmpl` calls the `sopsDecrypt` partial, which calls chezmoi's `output` template function to run `sops --decrypt ...` at template-render time. Chezmoi builds its full source state — rendering every `.tmpl` target, including this one — during `Read()`, before it applies (writes files / runs scripts) anything. This means **no** `run_onchange_` script, regardless of its numeric position, is guaranteed to have run before any `.tmpl` file's content is computed in the same `chezmoi apply` invocation: script 43's position number controls its order relative to *other scripts*, not its order relative to *template rendering*. A hard failure in `sopsDecrypt` (via chezmoi's `fail` function, or an unhandled `sops` exit) aborts `Read()` for the entire apply, which would block every other unrelated file and script from applying too — not an acceptable failure mode for a repo-wide bootstrap.

**Finding 3 groundwork**: the existing Pattern C container-isolation check (`claude-repo-permission-patterns`, Decision 4) runs once, at the moment `apply-claude-pattern c` is invoked, and only checks for `/.dockerenv` / `$REMOTE_CONTAINERS` / `$CODESPACES` / an explicit override flag. It says nothing about where the resulting `.claude/settings.local.json` write lands relative to the container boundary. The companion devcontainer (`claude-pattern-c-devcontainer/devcontainer.json`) currently bind-mounts the whole working tree (`workspaceMount`: bind, `target=/workspace`) with `mounts: []`, so `.claude/settings.local.json` written inside the container is the same inode as the one on the host checkout — the write outlives the container by construction, independent of anything the isolation check evaluates.

## Goals / Non-Goals

**Goals:**
- Fix all three findings with the smallest change that closes the actual gap, reusing existing repo idioms (`.chezmoiignore.tmpl` conditionals, `shellQuote`, devcontainer named volumes) rather than inventing new mechanisms.
- Leave every other behavior of the three touched capabilities (`secret-management`, `script-execution`, `cloudflare-tunnel-management`, `claude-repo-permission-patterns`) unchanged.

**Non-Goals:**
- Auditing or fixing every `| quote` call in the repo — only sites that interpolate a secret into a shell-execution context (enumerated in proposal.md - What Changes).
- Changing chezmoi's own template-render-before-apply behavior, or working around it generically — the fix is local to the one capability it currently affects (`cloudflare-tunnel-management`'s SOPS-decrypted files).
- Launching, orchestrating, or auto-detecting Pattern C's devcontainer (unchanged from the parent capability's existing non-goal).
- Retroactively cleaning this repo's own already-accumulated `.claude/settings.local.json`.

## Decisions

### Decision 1: Swap `quote` for `shellQuote` at each confirmed shell-context call site, no new abstraction
Edit each confirmed site in-place: `{{ keepassxcAttribute "X" "Y" | quote }}` → `{{ keepassxcAttribute "X" "Y" | shellQuote }}`, and likewise for the non-secret `quote` calls that share the same shell-variable-assignment line in those same files (e.g. `GITHUB_USERNAME={{ .gh_username | quote }}` in script 45 — not a secret, but sharing the fix keeps the file internally consistent and costs nothing, since `shellQuote` is a strict superset of safety for any string value).

**Alternative considered**: write a repo-specific `secretShellQuote` template function/partial that wraps `shellQuote` with an assertion the value came from `keepassxcAttribute`. Rejected: `shellQuote` is already a correct, chezmoi-native function for this exact job; a wrapper adds indirection without adding safety, and the review's own suggested fix ("use shellQuote for shell literals; keep quote only for JSON/TOML contexts") is a direct function swap, not a new policy layer.

**Confirmed sites** (shell-variable-assignment or shell-argument context, KeePassXC-sourced or otherwise runtime-shell-facing):
- `home/private_dot_zsh_secrets.tmpl` — `GEMINI_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `DAGGER_CLOUD_TOKEN`, `GITHUB_TOKEN`, `AZURE_DEVOPS_EXT_PAT`, `AZURE_DEVOPS_EXT_PAT_PERSONAL`
- `home/private_dot_config/mcp-env/private_localstack-mcp-server.env.tmpl` — `LOCALSTACK_AUTH_TOKEN`
- `home/.chezmoiscripts/run_onchange_after_darwin-45-setup-github-auth.sh.tmpl` — `GITHUB_USERNAME`, `GH_PAT`
- `home/.chezmoiscripts/run_onchange_after_darwin-46-setup-ssh-github.sh.tmpl` — `MACHINE_NAME`, `SSH_ENTRY_NAME`, `SSH_PASSPHRASE`
- `home/.chezmoiscripts/run_onchange_after_darwin-47-setup-azure-auth.sh.tmpl` — `AZURE_ORG`, `AZURE_USERNAME`, `AZURE_PAT`, `AZURE_ACR_REGISTRIES`
- `home/.chezmoiscripts/run_onchange_after_darwin-48-setup-azure-auth-personal.sh.tmpl` — `AZURE_ORG_PERSONAL`, `AZURE_USERNAME_PERSONAL`, `AZURE_PAT_PERSONAL`
- `home/.chezmoiscripts/run_once_after_darwin-83-login-atuin.sh.tmpl` — `atuin login -u ... -p ... -k ...` and `atuin store rekey ...` arguments

**Explicitly not touched** (non-shell context, `quote` is correct): `home/.chezmoi.toml.tmpl` (TOML config data), `home/dot_local/share/claude-plugins/**/*.json.tmpl`, `home/private_dot_gmail-mcp/gcp-oauth.keys.json.tmpl`, `home/private_dot_config/github-copilot/intellij/mcp.json.tmpl`, `home/.chezmoiscripts/run_onchange_after_darwin-90-update-hosts.sh.tmpl` (`HOSTS_DATA_FILE` is a repo-controlled path, not a secret, and the risk model in this change is specifically secret values — left as a documented judgment call, not silently dropped), `home/.chezmoiscripts/run_onchange_before_darwin-23-install-packages.sh.tmpl` (tap/formula names are repo-authored `packages.yaml` content, not secrets).

### Decision 2: `.chezmoiignore.tmpl` conditional skip, gated on the age key file's presence at render time — not a hard `fail`
Add a condition to `home/.chezmoiignore.tmpl`, following the file's existing "Claude LaunchAgent" templated-skip pattern, that ignores the SOPS-decrypted Cloudflare Tunnel targets (`.cloudflared/cert.pem`, `.cloudflared/<tunnel-id>.json`) when the age key file (`{{ .chezmoi.homeDir }}/Library/Application Support/sops/age/keys.txt` — the exact path `run_onchange_after_darwin-43-setup-age-key.sh.tmpl` writes) is not yet present on disk, using chezmoi's `stat` function (`{{ if not (stat $ageKeyPath) }}`, confirmed to return `<no value>`/falsy for a missing path and a populated map for an existing one). A `print_message "info"`-style note (or a warning printed by the age-key-install script itself, since `.chezmoiignore` cannot print anything) tells the user a second `chezmoi apply` is needed once the age key has been installed — consistent with this repo's existing "scripts SHALL be safe to re-run" convention (`script-execution`).

This turns a fresh machine's first `chezmoi apply` into: script 43 installs the age key (its own render-time content — the KeePassXC attribute — has no dependency on anything SOPS-related, so it is unaffected by this change), the Cloudflare Tunnel files are skipped for this run via `.chezmoiignore`, and every other file/script applies normally. A second `chezmoi apply` (already a normal, idempotent, safe-to-run operation in this repo) now finds the age key present, the `.chezmoiignore` condition evaluates false, and `cert.pem` decrypts normally.

**Alternative considered**: make `sopsDecrypt` (or `private_cert.pem.tmpl` directly) call chezmoi's `fail` function with an actionable message when the age key is missing, satisfying the "SHALL fail with an error identifying the missing dependency" branch of the (pending, unsynced) `sops-age-encryption` capability's own scenario. Rejected as the primary fix: a `fail` inside `Read()` aborts source-state construction for the *entire* apply, not just the Cloudflare Tunnel targets — on a fresh machine this would block script 43 (the very script that resolves the problem) from ever running, along with every unrelated file. The `.chezmoiignore` skip is the "OR gracefully skip" branch of that same pending scenario, and is the only one of the two that doesn't make the bootstrap worse than the bug it fixes.
**Alternative considered**: reorder script 43 to run earlier (lower position number). Rejected: per the groundwork above, template rendering during `Read()` is not interleaved with script execution by position number at all — renumbering does not change when `private_cert.pem.tmpl` is rendered relative to any script, so it would not fix the bug, only obscure it.

### Decision 3: isolate `.claude/` inside Pattern C's container with a named volume, and make `apply-claude-pattern c` verify that isolation at write time
Two changes, layered (structural default + runtime enforcement, mirroring this capability's existing Decision 4 philosophy of "structural, not just documented"):
1. `claude-pattern-c-devcontainer/devcontainer.json`'s `mounts` array gets an anonymous/named Docker volume mounted at `${containerWorkspaceFolder}/.claude`, layered on top of the existing working-tree bind mount. Anything written under `.claude/` inside the container — including `apply-claude-pattern c`'s own output — lands in that volume, not on the host checkout; it disappears with the volume's lifecycle, never touching the bind-mounted tree the host session sees.
2. `apply-claude-pattern`'s existing `has_container_evidence` check (Decision 4 of the original design) gets a second, independent check specific to pattern `c`: before writing, confirm `./.claude` is its own mount point (e.g. by checking `/proc/self/mountinfo` for an entry whose mount point resolves to `$(pwd)/.claude` — no extra package required, works in any Linux container) rather than being part of the same bind-mounted filesystem as the rest of the working tree. If `.claude` is not isolated this way, pattern `c` is refused with the same class of error as the existing bare-host refusal, pointing at the devcontainer template's `mounts` entry as the fix — this catches a devcontainer that bind-mounted the whole tree without the volume (e.g. hand-rolled, or the template edited without re-reading its header), not just a bare host.

**Alternative considered**: only fix the devcontainer template (item 1) and leave the runtime check as-is. Rejected: this capability's own prior design explicitly chose a structural, code-enforced check over a documentation-only warning for the exact same class of risk (Decision 4); doing so once for "is this a container at all" and not again for "is `.claude` actually isolated within it" would be an inconsistent level of rigor for what is otherwise the same threat model.
**Alternative considered**: have `apply-claude-pattern c` write outside `.claude/` entirely (e.g. a container-only env var enabling `bypassPermissions` without touching `settings.local.json`). Rejected: Claude Code's own permission model reads `defaultMode` from `settings.local.json`; inventing a parallel non-standard mechanism to avoid writing that file is a larger, riskier change for the same outcome the volume mount already achieves with a standard devcontainer feature.
**Alternative considered**: a container `postStop`/teardown hook that reverts `.claude/settings.local.json` on exit. Rejected: devcontainer tooling does not universally support reliable stop hooks across VS Code / the `devcontainer` CLI / other launchers, so this would be inconsistently effective at best silently unenforced at worst — the volume-isolation approach has no such dependency, since it prevents the write from ever reaching the host path in the first place.

## Risks / Trade-offs

- **[Risk] `shellQuote` changes the rendered byte content of every touched file, which could re-trigger `run_onchange_` scripts unnecessarily on the next `chezmoi apply` for machines that already ran them** → Mitigation: this is expected, one-time, idempotent-by-design behavior (`script-execution`'s existing "safe to re-run" requirement) — re-running `setup-github-auth`, `setup-ssh-github`, etc. once after this change lands is a correct and harmless side effect of fixing their content, not a regression.
- **[Risk] A `.chezmoiignore.tmpl` skip is easy to forget about — a user on a fresh machine sees no Cloudflare Tunnel files and no explicit error, only their absence** → Mitigation: script 43 already prints a `print_message "success"` line on completion; tasks.md will add a companion note there (or in the Cloudflare Tunnel setup script's own pre-check) surfacing that a second `chezmoi apply` is needed when tunnels are configured but `cert.pem` is still missing, rather than leaving the skip silent.
- **[Risk] The `/proc/self/mountinfo` isolation check (Decision 3, item 2) is itself a heuristic, spoofable by a determined user inside a hand-built container** → Mitigation: named explicitly as best-effort, same posture as the existing container-evidence check it extends (`claude-repo-permission-patterns` design already documents this class of check as "a heuristic, not a security boundary").
- **[Risk] The named-volume mount (Decision 3, item 1) means `.claude/settings.local.json` does not persist across container rebuilds** → Mitigation: accepted — Pattern C's whole premise is a disposable, sandboxed session; not persisting its permission state across rebuilds is the safer default, and a user who wants a stable per-project Pattern C posture can re-run `apply-claude-pattern c` after rebuild (already idempotent).

## Migration Plan

Purely corrective — no new files, no schema changes, no data migration. Deploys on the next `chezmoi apply` for every machine that already renders the touched templates/scripts (secret-rendering fixes apply on `ai`-tagged and other existing gates unchanged; the Cloudflare Tunnel fix applies only on machines with `cloudflare_tunnels` configured; the Pattern C fix applies only where the `claude-pattern-c-devcontainer` template has been copied into a repo's `.devcontainer/` and rebuilt). No rollback beyond reverting the commit and re-applying; the `shellQuote` change causes affected `run_onchange_` scripts to re-run once (see Risks), which is expected and safe.
